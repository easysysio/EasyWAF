From nothing to a protected site, in the order you would really do it. Put a site behind EasyWAF, give it HTTPS, watch what a policy would do to its traffic, deal with the first false positive, and only then enforce.
A step is marked done when this appliance already has what it describes, so you can leave and come back. The documentation's tutorial walks through the same steps at more length.
{{ self::step_head(n=1, done=done.site, title="Put a site behind EasyWAF") }}

A site is a hostname and where its requests go. Give it a name, the hostname visitors use, the address of your application as the Upstream, and HTTP port 80. Leave HTTPS and the policy empty for now.

The port is bound as soon as you save. With no policy the site is a plain reverse proxy: forwarded and recorded, not inspected.

{{ self::step_head(n=2, done=done.traffic, title="Send a request through it") }}

Before changing DNS, ask EasyWAF for the site by name and check that your application answers: 

curl -i --resolve shop.example.com:80:<this host's address> http://shop.example.com/

The request appears in Traffic Monitor marked PASSED. A 404 from EasyWAF means the hostname on the site is not the one you asked for; a 502 means it cannot reach the upstream.

Then point the hostname at this host, so every visitor arrives through EasyWAF.

Traffic Monitor
{{ self::step_head(n=3, done=done.https, title="Turn on HTTPS") }}

Let's Encrypt validates over port 80, which is why the hostname has to point here first.

  1. Set the ACME contact address under Settings, on the TLS tab.
  2. Open the site and press Request Certificate. EasyWAF answers the challenge itself; nothing changes on your application.
  3. Set the site's HTTPS port to 443 and choose the certificate.
  4. Check the site over https://, and only then tick Redirect HTTP to HTTPS.

Renewal is automatic. A certificate you already have can be uploaded in the Certificate Manager instead.

{{ self::step_head(n=4, done=done.policy, title="Create a policy that only watches") }}

Create a policy, leave its mode at DetectionOnly and the basic rule sets ticked, then choose it as the site's WAF Policy.

In DetectionOnly the rules run on every request and nothing is refused. You are about to find out what the policy would do before it does it. Prove it is looking: 

curl -i "https://shop.example.com/?q=xp_cmdshell"

The request reaches your application as usual, and its row in Traffic Monitor says WOULD BLOCK, with the rule that matched.

{{ self::step_head(n=5, done="", title="Leave it a few days, then deal with the false positives") }}

Give it long enough to see whatever your site does weekly. Then filter Traffic Monitor to what would have been blocked. Every row is either an attack — which you want refused — or your own traffic tripping a rule, which would have been an outage for that user.

For a false positive, take the narrowest answer that fixes it:

  1. For that caller — exclude for this IP on the row. Everyone else is still checked by the rule.
  2. For that path — an exclusion narrowed to a path prefix, under Rule Exclusions.
  3. For the whole policy — untick the rule on the policy's Rules tab.

When it is the caller that is trustworthy — your monitoring, a partner's integration — use Allow on the row instead, which skips every check for that address.

Traffic Monitor Rule Exclusions
{{ self::step_head(n=6, done=done.enforcing, title="Enforce") }}

When the only rows that would have been blocked are ones you are happy to block, set the policy's mode to On. The same request as in step 4 now gets a 403.

A blocked visitor sees a page with a reference — the time and their address — and nothing about which rule matched. That is on the row in Traffic Monitor, and the reference is how you find it when someone says they were blocked by mistake.

Policy Manager
{{ self::step_head(n=7, done=done.smart, title="Stop the ones that keep trying") }}

A scanner refused once tries again, two hundred times. Smart Protect refuses an address outright for a while once the rules have refused it a few times.

Before switching it on, use the preview on the Smart Protect page: it replays your recorded traffic and says how many of the requests it would have refused were in fact served successfully. Those are real users. Then tick Enable Smart Protect on the policy.

Smart Protect
{{ self::step_head(n=8, done=done.lists, title="Refuse known-bad addresses") }}

The published lists update themselves daily and do nothing until a policy switches one on. A reasonable start: Block hijacked netblocks, Challenge compromised hosts, and leave Tor exit nodes off unless you have a reason.

Challenge shows a CAPTCHA, so a wrongly listed address is slowed down rather than shut out.

IP Lists
{{ self::step_head(n=9, done=done.backup, title="Make sure you can get it back") }}

Everything you have set up is in one database. Switch on scheduled snapshots and press Take one now to see it work, and have your host's own backup copy the backups directory somewhere else.

A snapshot holds every private key and password hash; treat it as one.
